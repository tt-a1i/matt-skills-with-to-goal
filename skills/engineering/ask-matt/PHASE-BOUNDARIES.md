# Choosing a context boundary

Choose according to what the next task needs and what the current context can reliably carry. Phase boundaries are convenient review points, not a prerequisite for managing context.

| Need | Useful option |
| --- | --- |
| The current context is coherent and useful for the next work | Continue |
| An approved source should be inherited while execution logs stay separate | Fork, when requested and supported |
| Work must move between people, harnesses, or sessions, or history contains conflicting drafts | Compile a goal from the authoritative source |
| Important decisions exist only in the conversation and must travel | Record a focused handoff |
| The same task continues but the conversation has grown unwieldy | Compact while retaining decisions, source pointers, permissions, and remaining work |
| A concrete independent subtask can run alongside useful local work | Delegate when available and authorized |
| Nothing in the current conversation is needed again | Clear only after confirming that necessary context is durably recorded |

A fork inherits completed history; it does not compress it or isolate the filesystem. Send later decisions to the execution context explicitly. Durable specs, tickets, and code can already supply a handoff, so reconstruct from those when sufficient.

Use the harness's current context information and observed behavior instead of a fixed token threshold. Preserve the approved scope and evidence at every boundary.
